## Aprobaciones, Interacciones Y Efectos

- Approvals tienen estados `pending`, `approved`, `rejected`, `executing`, `executed`, `failed`, `expired`, `invalidated`. `resolve()` realiza claim condicional pending→approved/rejected. La ruta posteriormente marca approved→executing, valida fingerprint/argument hash, invoca herramienta y persiste resultado en pasos separados (`app/approvals.py:67-81`, `app/main.py:1327-1477`). Existe una ventana de fallo después del efecto externo y antes del resultado persistido; no hay evidencia de idempotency key/reconciliación general.
- Interactions nacen `pending`, expiran a `expired` o responden `approved`/`denied`; no tienen CHECK de estados. El runtime espera por polling y reanuda el stream tras la respuesta (`app/main.py:467-527`, `1430-1435`). Una interacción pendiente puede tener un run activo bloqueado esperando su respuesta.
- Runs pueden estar `started`, `running`, `waiting_approval` o terminales como `completed`/`failed`; no hay CHECK de estado ni tabla de worker queue. El estado `waiting_approval` acompaña a una aprobación reanudable. Reanudar una continuación puede volver a llamar proveedor, crear otra approval o persistir mensaje (`app/main.py:1393-1477`).
- No se observó tabla durable de retry, queue o delegation. Tareas/streams y efectos ya iniciados no se pueden inferir ni detener sólo mirando SQLite; se requiere parar/fencear procesos y egress antes de la futura transición.
- MCP/provider/tool calls son efectos externos. SQL no puede deshacer una llamada que ya ocurrió. Un registro `executing` no se debe marcar como invalidado hasta demostrar que el proceso fue detenido y que no quedan efectos en curso.
